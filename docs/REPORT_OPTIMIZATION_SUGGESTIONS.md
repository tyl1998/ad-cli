# 报告优化建议

记录时间：2026-05-18
背景：基于最近几次星巴克 App 自动化执行与报告复盘，总结当前报告系统最值得优化的方向。

## 总体判断

当前报告系统已经具备比较好的基础能力：

- 支持 `html` / `json` 双产物
- 普通执行命令可自动落盘为 execution
- `report note` 可补充 AI 判断
- `tap` 已支持自动截图留证
- Viewer 中已经开始具备“回放点击行为”的基础能力

这说明系统已经不只是“日志记录器”，而是在向“可复盘的自动化执行报告”演进。

接下来最需要优化的，不是单纯“记录更多数据”，而是：

1. 让人更快看懂报告
2. 让 case 状态更稳定
3. 让关键证据更突出
4. 让误操作和偏航更容易被识别

---

## 建议 1：报告应拆成“业务步骤层”和“原子执行层”

### 当前问题

现在报告主要以 `execution` 为核心记录单位。

也就是说，下面这些都会各算一步：

- `device info`
- `app info`
- `page info`
- `wait`
- `find`
- `dump`
- `tap`
- `report note`
- 重试
- fallback

这对排障有帮助，但对业务阅读不友好。

例如，一个用户看起来只是在执行：

1. 进入我的
2. 点击好礼券
3. 切到代金券
4. 查看是否存在 30 元代金券

但实际报告可能会膨胀为几十条 execution。

### 影响

- 报告看起来“步骤过多”
- 用户容易误以为 AI 做了很多无关操作
- 技术细节掩盖了真正的业务路径

### 建议

报告建议拆为两层：

1. `business_step`
   面向人类阅读的业务步骤

2. `execution`
   面向排障的原子命令日志

理想形态：

- 时间线默认展示业务步骤
- 展开某个业务步骤后，再看到其下关联的 execution 列表

例如：

```text
业务步骤 1：进入我的页
  - tap: 我的
  - screenshot
  - page info

业务步骤 2：点击好礼券
  - tap --xy
  - screenshot
  - page info

业务步骤 3：切换代金券分类
  - tap --xy
  - screenshot
```

### 预期收益

- 报告更接近“人类理解的测试步骤”
- 同时保留技术可追溯性
- 大幅缓解“为什么一个 case 有 40 多步”的观感问题

---

## 建议 2：`case-end` 与 `finalize` 之间必须增加强约束

### 当前问题

之前已经验证过：

- `report case-pass`
- `report finalize`

如果并行执行，可能出现竞态：

- suite 已 finalize
- 但 case 仍然是 `unfinished`

### 影响

- 报告整体看似成功
- 但 case 状态不完整
- 影响报告可信度

### 建议

在工具层面增加强校验：

1. `report finalize` 前先检查是否存在 `running case`
2. 如果有，则直接拒绝 finalize
3. 返回明确提示：请先执行 `report case-end`

### 可选增强

如果想更稳，还可以考虑：

- `finalize --force`
  自动把未结束 case 标为 `unfinished`

但默认行为仍建议是“拒绝 finalize 并提示修正”，不要悄悄吞掉状态问题。

### 预期收益

- case 状态与 suite 状态保持一致
- 报告不会出现“整体结束但局部未收口”的矛盾

---

## 建议 3：引入“证据检查点”机制，而不是默认每步截图

### 当前问题

虽然现在 `tap` 已经会自动截图，但报告里仍然存在一个问题：

- 哪些截图是关键证据
- 哪些截图只是普通操作留痕

目前没有很好区分。

### 不建议的方案

不建议所有 execution 默认强制截图，因为会导致：

- 报告体积变大
- 执行更慢
- 很多截图没有阅读价值

### 建议

引入“证据检查点”概念。

把截图分成两类：

1. `evidence checkpoint`
   关键业务节点的证据截图

2. `supporting screenshot`
   普通执行留痕

### 推荐设为证据检查点的场景

- 首页进入成功后
- 弹层出现时
- 弹层关闭后
- 关键入口点击后
- 商品加购成功后
- 切换分类后
- 进入结算/确认付款页后
- 发生 error / timeout / fallback 时

### 报告展示建议

在报告首页或 case 概览中，直接聚合显示这些证据检查点，而不是让用户自己从几十个 execution 里找截图。

### 预期收益

- 报告更适合业务复盘
- QA 更容易确认关键节点
- 保持截图数量可控

---

## 建议 4：点击行为需要更可解释

### 当前问题

即使现在 `tap` 带了 `spotlight`，仍然可能出现阅读上的疑问：

- 为什么点这里
- 这是结构化点击还是坐标点击
- 是正常点击还是 fallback

### 建议

为每次点击增加更明确的分类：

1. 结构化点击
   - `tap --id`
   - `tap --text`

2. 坐标点击
   - `tap --xy`

3. fallback 点击
   - 原结构化定位失败后退化到坐标

并且建议支持一个简短原因字段，例如：

- 点左侧好礼券区域，避开右侧去购买按钮
- `find` 命中失败，按截图视觉区域兜底
- 当前页元素分裂，避免误触购买 CTA

### 预期收益

- 报告更像“可解释执行过程”
- 更容易发现误点击原因
- 更方便优化 skill

---

## 建议 5：需要更强的“偏航识别”

### 当前问题

在 App 自动化里，很多问题不是报错，而是“点进了错误但合法的页面”。

例如：

- 点击 `好礼券` 区域，实际误进 `去购买`
- 点击后 activity 没变，但页面主体变了
- 进入商品购买目录，而不是持有券列表

### 建议

报告里应该显式标记这类情况：

- `unexpected_branch`
- `semantic_drift`
- `navigated_to_purchase_instead_of_inventory`

即使最终还能修正回来，这种偏航也值得被记录。

### 建议展示方式

在 case 概览里增加：

- 偏航次数
- fallback 次数
- 异常恢复次数

### 预期收益

- 报告不仅记录“做了什么”
- 还能帮助识别“哪里最容易误操作”

---

## 建议 6：`page info` 与视觉截图要并排展示

### 当前问题

仅凭 `page_after` 或 `activity`，有时不足以说明真实状态。

移动端经常会出现：

- activity 没变
- 但页面内容已经变了

### 建议

在关键 execution 的详情中，统一展示：

- `page_before`
- `page_after`
- 对应截图

尤其是这些步骤：

- `tap`
- `back`
- `scroll`
- `input`

### 预期收益

- 能更直观看出“页面是否真的切换”
- 降低对 activity 文本的过度依赖

---

## 建议 7：首页应增加“结论卡片”

### 当前问题

现在报告偏技术流水，缺少一个用户一眼能看的结果区。

### 建议

在报告首页或每个 case 顶部增加 `Summary Card`，包含：

- case 名称
- 最终状态
- 业务结论
- 关键路径
- 关键证据截图
- 偏航次数
- fallback 次数

### 示例

对于“查看是否存在 30 元代金券”这个 case，理想结论卡片应类似：

```text
状态：passed
结论：存在 30 元电子代金券
关键路径：我的 -> 好礼券 -> 代金券
风险提示：右侧“去购买”容易误点
关键证据：代金券分类页截图
```

### 预期收益

- 不需要先读 execution 才知道结果
- 报告更适合业务方、测试方快速查看

---

## 建议 8：报告命名与执行范围要一致

### 当前问题

如果报告名叫“双 Case 回归”，但实际上只执行并收口了 1 个 case，读者会误以为两个都完成了。

### 建议

报告顶部建议显式展示：

- planned cases
- completed cases
- running cases
- skipped cases
- unstarted cases

### 预期收益

- 报告范围更清晰
- 避免对执行覆盖范围产生误解

---

## 优先级建议

如果只选最值得优先落地的 3 项，我建议是：

1. `business_step` 层
2. `finalize` 前强校验 active case
3. `evidence checkpoint` 机制

原因：

- 第 1 项解决“报告太碎，不好读”
- 第 2 项解决“状态不稳，不可信”
- 第 3 项解决“证据不聚焦，不好复盘”

---

## 总结

当前报告系统已经具备较强的执行记录能力，但下一阶段最需要从“记录日志”进化到“组织信息”。

最关键的方向不是继续堆数据，而是：

- 把技术细节组织成业务可读的结构
- 把关键截图提升为证据
- 把偏航和 fallback 变成可观察指标

如果这些点逐步补齐，这套报告就会从“自动化运行产物”进化成真正好用的“测试回放与复盘系统”。
